# G: a real native preservation/completion family

## 1. Scope and preferred family

The selected runtime change is an adapter and controller generator inside the current `PolicyFinderWork`, not another solver or a change to Current's heuristic. Existing finite control, original-request acceptance, native options and independent checking remain the owners.

Prefer the existing **EldritchSideIntent** family for the first implementation when the actual request/session permits it. This is capability-based selection, not a rule keyed to armour names. It already supports real setup sequences and dirty target-side removal/reroll while opposite-side goals survive. Exalt additionally requires capacity and a real eligible missing goal. [R9–R10]

Do not reuse `phase_lower_eldritch_programs` as executable admission: it is a lower-model producer. Extract or expose the common descriptor/synthesis calculation under the original request and the ordinary executable scope checks. Keep real failure/cap statuses. No new hand-coded dominance or pool rules in Python/TypeScript.

Use ProtectedSide instead only if native permissions and every relevant lock/removal outcome are supported. The Protected Annul source comment is an explicit warning: a lock can be removed, so a fixed unconditional removal afterwards is not legal for all outcomes. Its cleanup-complete exclusion cannot just disappear. [R11]

## 2. Inputs and representations

Keep separate:

- exact original problem identity: native data/session/base/level, original item, GoalSpec, action/programme/dependency scope, prices and numerical acceptance;
- controller binding: requested held subset H, target side T, still-missing goals, native programme semantics, guard, control/continuation ports;
- proposal score: descriptive progress/obstruction information, with no value or proof authority;
- checked artifact: complete graph bytes plus exact evaluation and matching context.

The existing finder problem string/hash is a diagnostic label; do not assume it alone binds every price/data/scope dependency. Extend or supplement identity at the actually reused/accepted boundary rather than create a global identity service.

A requested coverage test is assembled from the **original** slots and threshold semantics. It must not change the GoalSpec supplied to `compile_finder_goal_condition`, `CalcContext::is_goal_state`, or the independent evaluator. Target-side count comes from the native cap and actual role sides, not an embedded `>=4` rule. Overlapping or unknown-side goal slots must be handled by the native representation or refused; a popcount assumption is not an injective matching proof.

## 3. Proposed internal seam (names are design suggestions, not existing APIs)

A narrow `FinderProgramBinding` may own:

```
original problem/scope identity
native PlannerOperator / fixed-option semantic identity
ordered mandatory runtime programme
original resource identities and quantities
observable initiation/continuation guard
held-goal obligation and exact entry-domain description
port declarations (normal, retained-context variants, loss/recovery)
```

`RunNativeProgram(binding_id)` in the current control graph is the proposed consumer. Start with only the selected programme kind. A variant that adds a dozen unused families is outside scope. Existing Scour/Alchemy remains a control.

Programme construction must use the real `build_planner_operators` / runtime-semantics and automatic-synthesis owners. Registry presence is not caller permission. Finite selected programme execution, expected resource accounting and independently evaluated flattened execution must agree before it is used in search.

The adapter must distinguish a truly requested programme from an arbitrary sequence of disabled primitives. Do not synthesize a new GoalSpec with widened action lists simply to make preparation accept the graph.

## 4. Dependency-only occurrence authority

The current `prepare_finder_candidate` admits only standalone requested primitives. A programme may use legitimate dependencies that are not standalone candidates, but supporting that case requires a **trusted occurrence**, not an untrusted JSON annotation.

The compiler should return graph bytes plus its owned occurrence manifest where needed. The preparation gate receives that trusted object from the native construction path. For every such occurrence verify the original permitted programme, parameter binding, exact emitted operations, ordered setup/cleanup, expected entry/exit ports and absence of unauthorized external jumps into its interior. A malicious raw JSON declaration cannot mint this permission. An ordinary graph without trusted provenance retains the current strict primitive-only gate.

For the initial family, avoid compiler optimizations that reorder, drop or coalesce dependency operations. Later sharing needs its own mapping proof. Every successful exit still reaches an effective original-goal guard. A default success edge with a decorative condition remains rejected.

Keep the native programme scope closed under its actual dependency contract, not under arbitrary combinations of all dependencies. Tests must reject the same internal operation at a new independent decision, wrong occurrence order, absent setup, skipped mandatory cleanup, changed parameter or cross-programme entry.

## 5. Initiation domains must be real

A program built at one concrete item is not thereby legal throughout a goal-mask region. Either:

1. its native descriptor/refinement contract proves legality and relevant effect for every item satisfying the guard; or
2. its guard is sufficiently specific and complete native evaluation checks all reached members, with unsupported members routed to an independently legal complete alternative or refusing the proposal.

Do not materialize one arbitrary coarse representative and claim the programme applies to all members. Do not replace a cap/refusal with a default goal. Persistent Eldritch state, existing crafted/fractured mods, blocker families, side capacity and hidden offer/checkpoint state remain relevant.

A MAY-survive summary only supports proposal ranking. A claimed preservation property for held goals requires the selected complete law or an applicable sound native contract. The audit hook should identify which grade was used.

## 6. The actual controller family

Generate from the original root, with normal supported acquisition choices and no hidden Current solve. The first generator should be small but meaningful:

```
ACQUIRE:
    original strict goal? -> SUCCESS
    held-side request/guard achieved? -> COMPLETE_OTHER_SIDE
    otherwise -> supported paid acquisition/recovery -> ACQUIRE

COMPLETE_OTHER_SIDE:
    original strict goal? -> SUCCESS
    held-side/context no longer valid? -> legal recovery/acquisition
    other-side requested progress incomplete?
        -> native-supported add / selective reset / capacity-opening programme
        -> COMPLETE_OTHER_SIDE or explicitly routed loss
    requested progress present but unwanted explicit occupancy remains?
        -> native-supported removal/cleanup programme
        -> COMPLETE_OTHER_SIDE or explicitly routed loss

SUCCESS:
    reachable only through unchanged original native goal guard
```

Do not treat the pseudocode as a PoE mechanic. Native capability/scope/laws choose the real actions and their admissible guards. In particular, not every goal family has a targeted add, not every cleanup is safe, and no candidate may rely on an unavailable law.

Two practical bindings make the test concrete. For A3, a native-held requested prefix side plus unwanted suffixes can exercise preservation during cleanup. For A5, required suffixes remain to be completed, so the same interface must support retaining the prefix holding while suffix progress is acquired, lost and recovered. At least one generated full-root graph must actually enter the dirty preservation branch with positive probability. A dormant branch in a graph is not a demonstrated capability.

One or two native choice variants within the selected family are enough initially. Do not enumerate every role subset and action Cartesian product. Admit at most two new complete candidates per solve inside the existing eight-total-attempt ceiling; choose bindings deterministically from declared native relevance, not a hardcoded goal index. Record this coverage change.

## 7. Prevent a cosmetic substitute

Required native positive witnesses:

- a dirty item reaches a nonterminal complete-decision boundary under the generated root policy;
- declared held requested goals survive the selected preserving programme's supported positive-probability outcomes, or loss is represented and paid explicitly;
- the controller takes a useful supported operation without resetting all valuable progress;
- a second binding with missing requested other-side progress needs genuine completion, not just a goal label;
- final clean target, resource cost and primitive count agree in independent root evaluation.

A Scour/Alchemy reset that destroys the holding, an operation never reached, a free advanced start, a count-only classifier, or a weaker terminal does not pass these requirements.

## 8. Lifetimes and resource semantics

Bindings, guards, occurrence manifests, compiler work, graph buffers, state-local synthesis and checker storage all belong in the finder aggregate. Include overlap with the old winner and active candidate. Use existing resumable native construction when expensive; do not hide a large synchronous synthesis in a status query. Track work cumulatively across attempts, including failed and censored ones.

One checker is active. Finish/cancel stops speculative expansion and preserves/returns only an already checked compatible graph under the existing lifecycle. Do not reenter WASM from message handling. An accepted graph and its programme provenance move together; a later rejected graph cannot inherit acceptance or retain stale flags.

## 9. Engineering result versus economic result

A valid narrow adapter with actual finder consumers may remain experimental even if it fails to beat Current. That is a completed representational capability, not economic superiority. Do not retain an unused framework or declare a missing intended family complete because a reset-only substitute works. The record must distinguish accepted branch coverage, full-root comparative cost, cap/refusal, and product activation.
