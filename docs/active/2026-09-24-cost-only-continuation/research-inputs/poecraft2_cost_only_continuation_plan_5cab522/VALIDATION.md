## 3. Economic witness and live integration are separate tests

L1 may use a saved current verified controller as an isolated oracle fixture. It
must record whether the parent search remains live and its real available headroom.
An offline success with more free memory cannot prove the live service fits.

L2/L3 must obtain the base through ordinary search in the current run before Finish.
A saved final controller first verified after the deadline is not such a precursor. No stored
strategy seeding, historical private state IDs or free partial start is allowed.
Record base graph/verification time, request/entry identity, complete candidate
program identity, full root check, adoption and final returned graph separately.

Compare the actual native full-root laws and old/new policy costs. Kernel equality
or lower local cost is not enough. Expected primitive actions are a separate
measured reward, not a new count-weighted objective or hard action limit.

## 4. Proportional execution order

First use saved evidence and focused fixtures. If needed, one unattended A5 control
resolves the baseline. One bounded L1 candidate batch is sufficient to select or
reject live integration. Then run one source-matched native off/on pair. A second
counterbalanced pair is for a real material or noisy timing/economic finding, not
an automatic soak.

After successful native integration, rebuild and run the affected source-matched
WASM/actual Calculator controls: primary final quality, first-policy/Finish
preservation and A4 stronger-controller preservation. Use a second role/context
fixture and at most one justified second full root. Do not run six roots per edit.

The first verified artifact must not be delayed by code that is nominally
post-incumbent: use source events, not only a UI sample. The final returned value
must not regress merely because the wave consumed time that ordinary search used
better. Existing setup/cancellation/Finish contracts and the accepted historical
ordinary-call limitation remain separately measured. Do not claim the 250-ms rule
passes; repeatable new latency deterioration needs its own disposition.

## 5. Success and failure labels

**Validated local opportunity:** a current controller improves in complete native
root evaluation; live affordability/discovery still separate.

**Native capability:** the ordinary-request native run reaches and retains that
improvement through the new bounded service inside original caps.

**Product capability:** actual source-matched compact Calculator run does so under
its own controls, while preservation passes.

**Material quality:** at least20% cheaper than the strongest compatible fresh
baseline. This is a planning target. Report any smaller strict improvement with
all costs and use an explicit activation decision rather than discard it on a
numerical threshold alone.

**No economic gain:** real candidate checked but old winner is no worse. This can
close the narrow candidate family, not all role-parametric planning.

**Missing premise:** no actual entry, unsupported complete option/router tail,
capacity failure or unimplemented bounded service. Name it instead of calling it
a numeric non-improvement.

## 6. Evidence and test discipline

Retain source/executable/WASM/data/request/economy/scope/treatment/cap and host
identity, raw outputs and omission counts. Reuse the existing isolated process
supervisor, runner and comparison tooling. Timed runs are serial; no LLM polling
proxy. Do not increase limits or disable diagnostics/controls only in one arm.

Independently evaluate changed controllers. Use owner-approved1000 Simulator
trials only when genuinely required for a changed controller, retaining every
censoring; do not resimulate unchanged policies. Rendered UI review belongs to
Oliver. Report all unrun or failed checks without substituting abstract examples
or build success for production correctness.
