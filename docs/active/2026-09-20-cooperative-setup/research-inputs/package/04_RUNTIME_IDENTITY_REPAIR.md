# 4. The narrow clean-host identity repair

## Observed, inferred, unknown

**Observed:** the new Windows job selects Python correctly, fetches the pinned twelve sources, produces the corpus-expected database data hash, validates six spec fixtures, compiles the complete runtime, then refuses its manifest hash. No downloadable artifact was present for that run. [R06–R09, R22](SOURCES.md)

**Source-confirmed:** the test wrapper parses the lock using default `ConvertFrom-Json`; `Invoke-ProjectPython` binds a string array; the timestamp property is passed as the compiler's `--generated-at-utc`; that compiler writes the received value verbatim into its deterministic manifest JSON. [R06, R08]

**Leading hypothesis:** timestamp parsing/coercion at that shell boundary changes the manifest's timestamp spelling. Microsoft's primary documentation says the default timestamp representation is DateTime and the `String` behavior preserves strings. The configurable `-DateKind` parameter was introduced in PowerShell 7.5. [P01]

**Unknown:** the failed run's actual manifest hash, timestamp, other field differences and payload bytes. Matching database data hash does not prove matching manifest bytes. Do not call the hypothesis confirmed until the arguments and generated bytes identify the difference.

## Smallest useful experiment

Run the supplied [PowerShell argument probe](checks/probe_timestamp_argument.ps1) with the **same PowerShell executable and selected Python** as the failed workflow. It reads the lock and prints the original string, parsed type, string-array-bound argument and Python-received argument. It does not fetch data, build native code, modify the repository or regenerate the manifest. It deliberately does not rely on the newer `-DateKind` option, so it can reveal differences between supported shell versions.

This review environment has no PowerShell; that probe has not been executed here. A nonzero diagnostic exit means the argument spelling differs, not that all other identity obligations are satisfied.

Next preserve the existing failed output or reproduce the existing pinned fetch→ingest→compile path into a **new** scratch directory. Do not replace `data/compiled/current` to obtain a convenient comparison. Use [inspect_runtime_identity.py](checks/inspect_runtime_identity.py) with the original lock, the actual artifact directory and, when available, the independently preserved reference manifest. It checks exact manifest SHA, literal timestamp, both payload SHA/lengths and manifest declarations, and reports explicit JSON-pointer differences when a reference is provided. This is an offline diagnostic, not a new source of canonical authority.

## Repair only what the evidence identifies

If the timestamp differs but the rest of the manifest and payloads match, preserve the literal lock field across the shell boundary. The existing selected Python's `json` loader is one compatible way to extract the string for all supported PowerShell versions. A tiny validated helper in the current tooling owner is preferable to regex extraction, shell-dependent reformatting or a new general manifest framework.

`ConvertFrom-Json -DateKind String` is another documented option only when the already-supported shell contract includes that parameter. Do not silently increase the minimum PowerShell version. Preserve the original string; reformatting an equivalent instant is not necessarily identical bytes.

If another manifest field differs, identify its source: compiler/schema version, normalized payloads, source identities, row counts, enum ordering or serialization. Do not infer that every mismatch is a newline issue. The compiler uses explicit UTF-8 bytes; scoped Git raw-byte rules already preserve fixture blobs. A payload mismatch is a different problem from a metadata-only mismatch.

## Required regression and evidence

Test the real wrapper's timestamp argument with a literal `Z` value and a nonzero-offset timestamp fixture; both should preserve their exact string under the supported shells. Test malformed/wrong-type lock data explicitly. Keep altered timestamp and payload inputs failing their pinned checks. A semantic comparison can explain a failure but never replaces a raw-identity contract.

Retain the failed manifest, its SHA, literal/parsed/bound/received timestamps, PowerShell version, actual Python path/version, source/data identities and both payload hashes. On failure the existing workflow should retain a small identity diagnostic through its existing reporting/artifact mechanism, not an unrelated all-purpose observer.

The current workflow contains no downloadable failure artifact; adding a narrowly scoped diagnostic upload is a proposed change, not a facility already used. Do not claim a new hosted pass until a future actual run establishes it. Local clean-checkout qualification can establish the local result without authorizing a push.

## Why this does not replace the main programme

This failure blocks trustworthy fresh qualification and must be resolved first. Its source-supported candidate cause is small. Once repaired, leave validation architecture alone and advance to two-owner setup. A raw identity guard doing its job is not a reason to weaken evidence checks or return to the completed retained-pool migration.
