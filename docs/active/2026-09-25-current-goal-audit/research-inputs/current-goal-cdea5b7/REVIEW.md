# Review and next-direction decision

## 1. The K result is real, narrow, and not a Current solver improvement

The K record at the reviewed head reports 19,667 A5 seed-selector calls, all outside the proposed first-policy gate because an output incumbent object existed. High-impact and incremental generation were enabled. There were no gate-on row comparisons. The correct result is `measured_gate_inactive`, not an active-gate no-reversal result, and not evidence that the old heuristic has been repaired. Repeating the same S experiment without a changed activation premise is not selected. [R2–R3]

The new experimental `conditional-retention` Finder builds a paid, original-root Eldritch held-side controller and validates every reached programme entry. Recorded original-root costs:

The new A5 candidate uses about 812 MB of selected owned memory and reaches its best at about 49.72 seconds, finishing around 56.57 seconds. These are recorded native experiments, not an actual four-minute Calculator qualification. The Finder's Current-oriented corpus status expectations are false even though each returned graph passed its independent policy check. The original record keeps that distinction. [R3]

The result shows that a missing strategy family can matter enormously to a weak finder. It does not show that Current lacks all preserving programmes, that this controller would improve Current, or that Current's target should be changed. Current already produces a much cheaper clean A5 controller.

## 2. The semantic boundary is confirmed

The direct parent of `2b8d5ac` is `82224d0...`. At that parent, both `CalcContext::is_goal_state` and the inspected compiler success condition use rarity plus the requested satisfied-slot threshold. The boundary commit adds the explicit-affix equality. The current source still requires that equality. [R4–R8]

For ordinary valid disjoint goal-slot domains, write:

- `C(x)`: requested rarity and enough requested slots satisfied;
- `g(x)`: number of satisfied requested slots;
- `n(x)`: total occupied explicit prefixes and suffixes;
- `T(x) = C(x) && n(x) == g(x)`: today's clean terminal.

The change turns states in `C \ T` from terminal to nonterminal. Their native continuation can require paid cleanup, preserved-side operations, risky removal, reacquisition and recurrent decisions. This is a change in the SSP/property, not a consequence of using an exact numerical algorithm.

The change also happened within the same v1 request vocabulary: a v1 label alone does not make old and new targets equivalent.

The commit was intentionally authored as an exact-explicit-item contract. It also changed carrier scheduling, compilation, option exits and proof models. Therefore a before/after runtime difference across that commit is not a one-factor experiment. A historical source audit is warranted; reverting the entire commit is not. [R4,R7]

## 3. Important counterevidence against a total historical explanation

Immediately after the change, the clean zero-to-five Conquest witness already had an independently evaluated 87,361.1690420501-Chaos controller, with lower 36.4286171890906. It was explicitly bounded, not optimality closure. It used a 60-second requested Finish, an approximately 71.88-second native solve, and an Imprint-enabled scope. Those numbers are not directly comparable with today's product profile. They do establish a strong clean controller at the semantic boundary. [R7]

Before the change, the parent record already describes difficult proof and runtime behaviour: the four-goal direct candidate cost 2,823.05, its former coarse lower/estimate 2,889.77 did not reconcile and was not retained as a lower, native acceptance took about 174 seconds, and WASM had large refinement memory and a 47.45-second worker slice. The easier terminal did not make every earlier problem easy or exact. [R9]

The right conclusion is: the change can explain a meaningful **model-related part** of the difficulty; its magnitude and relation to later regressions remain unmeasured. Other causes demonstrably existed on both sides.

## 4. Calculator: native consistency and product expectations are different

`pc_calc_action_outcomes` reports per-slot satisfaction from the distribution and computes `success_probability` by summing entries satisfying `calc.is_goal_state`. Thus positive requested-mod coverage and zero clean success can coexist without any probability bug. The exact supplied ~0.35% example lacks its complete frozen request in this message; do not claim to have reproduced that number. [R11]

For a choice-free one-action fixture, compute from the SAME complete distribution:

1. per-slot marginals;
2. joint requested coverage `P(C)`;
3. complete declared target `P(T)` or `P(E)`;
4. `P(C && !T)` and the reasons for failed occupancy.

Do not multiply marginals. Do not infer all-goals probability from a single marginal on a multi-goal request. Do not treat a truncated returned sample as the complete support. For observed-choice actions, fix and disclose the choice interpretation separately; use a choice-free action for the initial regression.

The product reference currently describes combined success as rarity plus the slot threshold and omits the extra-affix restriction in that section. That wording is inconsistent with the current native definition and should be corrected now, independent of any future default decision. [R12]

## 5. The crucial safety issue in a loose-target diagnostic

Changing only `is_goal_state` is unsafe. The emitted goal condition, fixed-option termination, gated reforge classification, original-target checks, compatibility identities and clean-target lower producers also depend on the terminal contract. [R8,R10,R13–R17]

A lower valid for the harder clean task need not lower-bound the easier coverage task. For example, one paid acquisition costs 1 and produces coverage with junk; cleanup costs 100. The clean value 101 is not a valid lower for the loose value 1. Setting the new goal's local lower to zero without rechecking its predecessors is not enough: a stale root lower can remain too large.

The experiment therefore needs a target-aware native contract and an explicit proof-capability map BEFORE long comparisons. Unavailable proof support is recorded. It is not converted into success, exactness, or silently substituted data.

## 6. Selected next programme

E0–E3/E5 are a bounded Current-solver semantics and comparability programme. E4 traces one same-clean-target construction boundary from the measurements; a small Current repair is permitted only if that trace provides the relevant native witness. No Finder expansion is selected.

The deliverable is not an assertion that allowing junk is better. It is a durable answer to four questions: what task each result solves, how much the terminal restriction changes current computational behaviour, whether an explicit occupancy encoding preserves today's exact target, and which Current consumer actually loses a useful complete continuation.
