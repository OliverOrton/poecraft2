# Shared native selective-completion family

## 1. First family and what it is not

Start from the existing K retained-side controller. The initial *new family* may restrict itself to all-required, disjoint, fixed-side goal slots on native-eligible Rare contexts; record that as proposal-family eligibility, not a global action restriction or a limitation of the whole evaluator. Any-k or unsupported mixed-side requests retain existing search and receive an explicit ineligible result for this family. Hold its root acquisition method fixed initially. Add complete candidates that distinguish:

- requested final target already met;
- the intended protected-side requested goals still present;
- target-side requested goals missing and real capacity available;
- target side full/blocked or covered but with unwanted explicit affixes;
- relevant paid setup/dominance already established versus still required.

Bind actual native Eldritch side-intent programmes for fill (Exalt), remove/cleanup (Annul) and reroll (Chaos) where supported and admitted. The source already constructs these programme kinds. This is not a new crafting mechanic and not a claim that any particular action is always cheaper.

The K baseline uses Chaos for acquisition; picks the side with more goals; and uses a target-side count threshold that can send intact held progress back to Chaos. The first treatment tests completion logic, not all of acquisition, side selection, ranker and proof simultaneously. Later a predeclared sibling may switch which eligible complete goal side to hold; do not manufacture a side with no native support.

Do not copy a saved A5 strategy, use a prefractured item for free, or read archive state IDs as search hints. Programmes are generated from the actual root problem and native descriptors. Diagnostic advanced states are contract fixtures only.

## 2. Reuse the existing control representation

`FinderControlGraph`, `FinderProgramBinding`, `compile_finder_control_json` and reached-entry checks are retained assets. Either make a minimal neutral naming/location adjustment or introduce a thin view over them; do not create a second graph IR and keep both forever.

A conceptual (not existing ABI) producer interface is:

```
Advance(problem, exact_root, family_configuration, resource_allowance)
  -> Incomplete(owned_cursor)
   | Complete(owned_candidate_with_native_occurrences)
   | Unsupported(typed_reason)
   | ResourceDeferred(typed_cap, spent_work)
```

The result contains a full-root finite control graph with trusted programme occurrences, exact problem/context identity, and generation provenance. It has NO verified-cost or proof-valid flag. A checker supplies acceptance. Call-local action/state indices may exist only within their owning context; exported identity uses complete semantic keys and exact root/bindings.

The producer does not know whether Finder or Current called it. It does not call either search solver internally. Its dependencies are the resolved native problem, approved action/option constructors, compiler control vocabulary and budget callbacks.

## 3. Complete branch semantics

A candidate can use the following structural policy, with every line specialized through actual native data:

```
if requested final target holds:
    Goal
elif protected holding is absent:
    paid acquisition, then assess again
elif target-side requirements are missing and native fill is admissible:
    selected setup/fill programme, then assess again
elif target side needs cleanup or capacity and native removal is admissible:
    selected setup/removal programme, then assess again
elif native side reroll is admissible:
    selected setup/reroll programme, then assess again
else:
    the explicitly compiled complete recovery alternative
```

This is a family of candidate *choices*, not the uniquely optimal rule. A candidate may prefer a reroll instead of filling when the actual economics warrant it. Generate a small declared set of such complete variants and let native checking compare their total cost.

For the first strict-clean family, an untouched held side must itself have no permanently unhandled unmatched affix. Three held prefix goals on a three-prefix-cap item satisfy that naturally. With fewer held goals, either guard the held-side occupancy appropriately or supply a complete cleanup branch; do not create a programme that can never reach the strict goal. For coverage R the terminal differs, but a comparable grammar still uses actual target assessment.

Every state that fails an initiation guard must route somewhere defined. A fallback to Chaos is allowed only if that operation is actually legal and all its subsequent behavior is covered by the graph. Routing to node zero does not reset physical state or remove Eldritch context.

## 4. Native programme admission and observations

Native side-intent admission checks actual rarity, side capacity, strictly preserved opposite goal support, eligible target members and paid dominance setup. It may differ among physical members with the same goal counts. The producer's first example does not authorize all instances of that role pattern.

Use the existing every-reached-programme-entry validation. For each actual reached native entry, validate a matching complete programme semantic key, expected resource vector, legality and held-goal preservation on all exits. Unobservable or unsupported hidden checkpoint/offer contexts are refused rather than guessed.

The compiler's graph-bound occurrence controls dependency-only operations. The complete operation sequence, setup and cleanup may not be entered in the middle or reordered by a JSON label. Preserve the shared original-goal success guard and exact root check. New predicate variants may reuse existing TestSlot, side-count and tier tests; if a narrowly needed predicate is missing, extend the existing native condition vocabulary and its evaluator/Simulator correspondence tests, not a frontend-only implementation.

The explicit target assessment remains reversible. If a target-side goal is lost, the candidate returns to a branch where that requirement is missing. Never carry an irreversible `acquisition_complete` bit that masks later loss.

## 5. Cooperative construction and memory

The existing K root `outcomes()`/automatic admission path is synchronous. Do not expand that into an unbounded multi-case loop. Reuse current advance/cancel APIs for expensive selected native laws and state-local admission. A retained factory cursor belongs to one owner and is included in aggregate live/peak memory and cumulative work.

Charge exact distribution construction, candidate control, trusted occurrence metadata, parsed graph, validation contexts, checker and accepted old policy concurrently. Reserve growth before allocation. No work refund on cancellation/rejection. The parent may already occupy most of 1 GiB; a standalone success is not a live Current success.

Initially retain only the candidate being generated and a bounded complete frontier. Reuse existing native caches within the same valid context, not a new general graph-response cache. Distinct bindings' probabilities and values remain distinct. Exact storage equality and logical work identity are not interchangeable.

## 6. Minimal family configurations

Initial production of proposals is bounded to:

- **K control:** existing retained-side reroll/removal graph, unchanged.
- **Fill-then-reassess:** use admitted side-add when capacity and a missing target exist; fully model subsequent junk/full-side outcomes.
- **Retain-and-repair:** add a native removal/capacity step before another fill when that complete programme is supported.
- **Reroll-versus-repair sibling:** compare the actual recurrent choice in a declared observed state class, retaining the same acquisition and held-side requirement.

These are at most four distinct structural configurations before feedback. Not every request admits each one. Unsupported is not a failed economic candidate; capped construction is censored; exact duplicates are identified before duplicate checking when a complete identity permits it.

First perform same-eight-attempt comparisons. A separate 24-attempt experiment may expand eligible side choices, one return rule or one compatible acquisition alternative after the initial completion family is understood. Do not broaden all dimensions together or turn the 24 ceiling into a claim of equal eight-check computation.

## 7. Shared candidate checker/adoption seam

The selected candidate is checked against the original request with the compiler-owned ingress contract, exact root, native permitted programme occurrences and original prices. The whole complete graph passes independent evaluation and every reached programme-entry validation. Record properness, cost, primitive count, missing mass and actual numerical acceptance scope.

Finder adopts the result in its existing checked-policy owner. Current's adapter creates a root-only executable incumbent through the existing retained portfolio. Neither receives statewise values for other items merely from the root result. Shared checking does not create shared proof authority.

A candidate can be semantically acceptable for R but rejected for L. A graph checked under one price snapshot cannot transfer its scalar value to another. Exact root implicit flags, empty implicit lists and persistent context are mandatory after the U repair.

## 8. Required evidence before economic claims

A native reached-entry record must show a nonterminal state holding the intended valuable side with an open or reparable target side; the new graph chooses a different complete programme there; all resulting exits remain covered; and the independent root result records its real cost. This can be positive or negative economically.

A hand-authored advanced-state test demonstrates initiation/preservation, not full-root acquisition cost. A dormant operation in a graph demonstrates neither. A large reduction relative to a weak Finder baseline does not by itself outperform Current. These distinctions must appear in the final report.
