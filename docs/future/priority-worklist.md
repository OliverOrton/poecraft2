## Ranking Rules

- **P0 — trust or baseline blocker:** possible incorrect behavior, an
  unreproducible product result, or a repository acceptance failure.
- **P1 — exactness or iteration multiplier:** directly advances exact solving
  or materially reduces the cost of learning why it fails.
- **P2 — maintainability and measured simplification:** valuable debt work
  that should follow a stable behavioral boundary or a confirming census.
- **P3 — product depth or later research:** worthwhile after the current
  correctness, exactness, and iteration boundaries are healthier.

Within a priority, dependency order wins over list order. A new reproduced
correctness issue may preempt every performance item.

## P1 — Exactness And Faster Iteration

### P1.1 — Engine-owned action-family controls and ablation mode

**State:** completed 2026-08-27. The native/WASM/Calculator contract covers
direct primitives and generated dependencies, defaults to unrestricted, and
discloses restricted exactness. The first PDR ablation found temporary Bench
was not the owner of the 299,394 alternative obligations: disabling it moved
the stop earlier to a 1 GiB strict-carrier construction cap after 43,535 exact
states, before alternative obligation construction.

**Why now:** action IDs can already scope primitive candidates, but the public
action description does not expose one stable engine-owned family label and
generated compound options need consistent dependency-aware filtering. The
PDR case currently creates 299,394 strict alternative obligations; family
ablations are the cheapest way to discover which admitted families amplify
that proof.

Add a typed allow/deny family control covering at least:

- ordinary currency;
- permanent Bench and temporary Bench blocker programs separately;
- metamod/protected programs;
- Essence;
- Fossil;
- Harvest reforge and Harvest augment/conversion;
- Eldritch primitives and automatic side-intent programs;
- Influence Exalt;
- Fracture and its recovery programs;
- Veiled crafting; and
- generated Imprint programs, retaining the existing dedicated toggle.

Requirements:

- the engine, not TypeScript ID prefixes, owns family classification;
- a generated program is unavailable when a required primitive family is
  disabled;
- result scope explicitly says it is exact/bounded only within the selected
  action envelope;
- disabled families remain visible in telemetry with a named reason; and
- default Calculator behavior and existing hashes remain unchanged when no
  override is selected.

Ship diagnostic/advanced controls before treating them as ordinary product
preferences. The first matrix should be the single PDR witness, not a broad
corpus.

### P1.2 — Cooperative, resumable broad destructive rows

**State:** completed 2026-08-27. Exact V3 broad rows now use deterministic
retained continuations, bounded cooperative slices, and publish only after
full completion. Resumed/uninterrupted, cancellation, cap, memory, and
telemetry controls pass.

**Why now:** the 100M PDR run contained a 102.40-second native solve step.
Raising caps increases that stall and does not materially advance proof.

Split the V3 exact broad-row recurrence into deterministic bounded slices with
an explicit cursor and retained scratch state. A partial row must never publish
or consume proof authority. Cancellation, cap refusal, and resume must retain
the same final row bits, ordering, probabilities, hashes, and logical-work
accounting as uninterrupted evaluation.

Initial acceptance should include:

- a small exact uninterrupted-versus-resumed oracle;
- interruption at multiple recurrence/component boundaries;
- deterministic cap accounting without overrun publication;
- bounded retained memory; and
- a material reduction from the current 102-second maximum PDR work item.

This is useful even if total work does not fall: it restores cancellation,
progress visibility, fair scheduling, and a stable checkpoint boundary.

### P1.3 — Development-only deterministic checkpoint/replay

**State:** highest-priority dedicated follow-up. A representation audit
rejected fake request/result or sparse-row caching. Honest replay must capture
the joint calculator/admission state at the coarse boundary and the oracle,
partition, proof/dependency, kernel/cursor, and incumbent state at the strict
boundary.

**Why after P1.2:** the repository intentionally deferred disk replay until
the proof-carrying quotient representation stabilized. Same-side exact closure
is now deterministic, but broad-row resumability should land first so the
checkpoint does not freeze another monolithic work representation.

Support at least two development checkpoints:

1. the completed coarse graph, selected policy, verified incumbent, and exact
   carrier inputs immediately before strict refinement; and
2. the first closed strict partition plus its obligation ledger, row kernels,
   and resumable row cursors.

Every checkpoint must bind and validate:

- source/format version;
- compiled artifact and canonical data identities;
- goal, start item, economy/prices, candidate action IDs, generated options,
  and solve profile/overrides;
- stable state/action/layout identities and floating-point contract; and
- completeness checksums for every serialized table.

Mismatch must refuse replay. Checkpoints are development acceleration only:
they cannot become product proof, publication, or cache authority without a
separate qualification. A clean replay must reproduce deterministic values,
rows, transitions, hashes, and exact-evaluation output.
